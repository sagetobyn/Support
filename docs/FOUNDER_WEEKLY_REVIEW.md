# Founder Weekly Product Review

## Purpose

This ritual protects Wembro from becoming a broad ecommerce dashboard before the first wedge has proof.

Wembro's current customer promise is the CSV-first Revenue Leakage Control Center for Indian D2C sellers: COD/RTO/NDR profit recovery, daily action, and savings proof. Long-term AI Operations OS work is future architecture unless it strengthens that wedge with evidence.

Every project is judged by five standards:

1. Data reliability.
2. Seller clarity.
3. Operational action.
4. Trust proof.
5. Savings evidence.

If a project cannot improve at least one of these standards for COD/RTO/NDR profit recovery, it is not active product work.

## Review Inputs

Bring these before the meeting starts:

- Current project list with owner, branch, status, and customer-facing promise.
- Latest seller evidence: CSV samples, audit notes, pilot observations, support notes, or user session findings.
- Screenshots or demo path for any visible product change.
- Test/build status for implementation work.
- Known non-goals or product-law risks.

Do not review vague roadmap ideas without evidence. Put them in future architecture notes, not the active build queue.

## Scorecard

Score each project from 0 to 4 in each category. Maximum score: 20.

| Standard | 0 | 2 | 4 |
| --- | --- | --- | --- |
| Data | No real input, no schema clarity, or unreliable sample data. | Uses CSV/sample data but has gaps, low-sample warnings, or unclear lineage. | Uses reliable seller/audit/demo data with visible quality checks and source context. |
| Clarity | Seller cannot tell what changed or why it matters. | Seller sees the issue, but wording or priority is still fuzzy. | Seller can quickly answer what is leaking, why, and what matters today. |
| Action | Output is passive reporting or a vanity dashboard. | Output suggests action but does not prioritize ownership, timing, or next step. | Output creates a clear daily action, decision, queue item, or review step. |
| Trust | Claims are black-box, overstated, or unsupported. | Claims include partial formulas, warnings, or audit trail. | Claims are transparent, auditable, privacy-safe, and honest about estimates versus verified outcomes. |
| Savings | No connection to money saved, protected, or lost. | Shows estimated INR impact but weak confidence or unclear formula. | Shows expected or verified savings with formula, confidence, before/after result, and seller-friendly explanation. |

## Decision Thresholds

| Score | Decision | Founder action |
| --- | --- | --- |
| 17-20 | Continue | Keep building, but preserve the COD/RTO/NDR wedge and proof loop. |
| 13-16 | Narrow | Continue only after cutting weak scope and writing the next proof artifact. |
| 9-12 | Pause | Stop new implementation until the owner fixes the lowest categories with evidence. |
| 0-8 | Kill or demote | Remove from the active roadmap, move to future architecture, or archive as a non-goal. |

A low score means pause or kill. It does not mean "keep building and explain later."

## Automatic Pause Rules

Pause immediately if any project:

- Claims real WhatsApp sending without provider integration, template approval, opt-out handling, and audit proof.
- Claims real courier API pushes without provider integration, execution status, retry handling, and audit proof.
- Claims Shopify/WooCommerce sync without implemented ingestion, mapping, and freshness checks.
- Claims ML prediction without trained data, evaluation, calibration, and clear labeling.
- Promises guaranteed ROI or verified savings without seller-specific evidence.
- Expands active product scope into inventory, returns, settlement, marketplace health, cashflow, chatbot, or broad AI agents before COD/RTO/NDR proof is stronger.
- Breaks the required sequence: Data -> Insight -> Decision -> Action -> Learning.

Automatic pause projects can restart only after the false promise is cut, demoted, or converted into a clearly labeled placeholder.

## Sample Agenda

Use a 45-minute weekly review.

| Time | Topic | Output |
| --- | --- | --- |
| 0-5 min | State the wedge | Confirm the week is still centered on CSV-first COD/RTO/NDR profit recovery. |
| 5-15 min | Review seller evidence | List the strongest data, pilot, audit, or demo signal from the week. |
| 15-30 min | Score active projects | Score each project on data, clarity, action, trust, and savings. |
| 30-38 min | Pause/kill decisions | Pause low-score projects and cut false promises or broad scope. |
| 38-43 min | Choose next proof artifact | Pick one artifact that improves seller trust: report, queue, savings ledger, audit trail, or review note. |
| 43-45 min | Assign owners | Record owner, branch, next action, and validation command. |

## Required Meeting Notes

For each reviewed project, write:

- Project name and owner.
- Score by category and total score.
- Decision: continue, narrow, pause, kill, or future architecture.
- What got cut or demoted.
- What became clearer for the seller.
- What proof, action, or trust artifact improved.
- Next validation step.

## Example Review Note

```text
Project: Weekly Founder Report
Owner: Product/Engineering
Score: Data 3, Clarity 4, Action 3, Trust 4, Savings 3 = 17
Decision: Continue
Cut/Demoted: No real WhatsApp automation language. No broad operations OS claims.
Seller Clarity: Founder sees top leakage driver, top actions, and estimated savings for the week.
Proof/Action/Trust: Report labels savings as estimated unless verified in the savings ledger.
Next Validation: Run npm test and npm run build after implementation.
```

## Founder Rule

The founder weekly review is allowed to stop work. A paused project is not failure; it is product discipline. Wembro earns permission to expand only after the current recovery control room proves that seller data becomes insight, insight becomes a decision, the decision becomes action, and the action creates trusted savings evidence.
