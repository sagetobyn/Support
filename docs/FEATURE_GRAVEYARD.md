# Feature Graveyard

This document exists to stop Wembro from resurrecting broad, noisy product ideas before the first wedge has proof.

Current product law:

- Wembro is the post-checkout profit recovery control room for Indian D2C sellers.
- The active wedge is CSV-first COD/RTO/NDR leakage recovery.
- The operating sequence is Data -> Insight -> Decision -> Action -> Learning.
- Long-term AI Operations OS language is future architecture, not the current customer promise.

If an idea does not improve COD/RTO/NDR data reliability, operational clarity, daily action, savings proof, or seller trust, it stays out.

## Non-Current Ideas

| Idea | Decision | Why it is not current | Unlock condition |
| --- | --- | --- | --- |
| Generic chatbot | Killed for current product | Chatbots create a support product, not a profit recovery control room. They blur the wedge and invite vague AI claims. | Only reconsider as a narrow NDR/COD response helper after real provider integration, opt-in, audit logs, and seller proof exist. |
| Shipping aggregator | Killed | Aggregation means labels, rates, courier allocation, wallet, reconciliation, and support liability. Wembro must sit above existing shipping stacks first. | Only reconsider if repeated pilot data proves sellers need action recommendations tied to courier selection and existing partners cannot cover the workflow. |
| Store builder | Hard no | Storefront creation is pre-checkout commerce infrastructure. It does not rescue failed COD delivery, NDR, or RTO leakage. | None for this product line. Build elsewhere if needed. |
| Inventory module | Postponed | Inventory is a real seller pain, but it is a separate operating loop with stock, procurement, and forecasting complexity. | After the RTO/NDR wedge has repeatable paid pilots and inventory data is available from trusted sources. |
| Returns module | Postponed | Post-delivery returns are not the same as RTO/NDR. Mixing them now hides the sharper failed-delivery rescue problem. | After COD/RTO/NDR savings proof is strong and return-reason data can be tied to verified financial outcomes. |
| Settlement recovery | Postponed | Settlement, fee deductions, remittance, and courier invoice mismatch need accounting-grade evidence. Current proof is shipment and action based. | After server storage, audit governance, reliable settlement imports, and seller-specific reconciliation proof exist. |
| Cashflow control | Postponed | Cashflow becomes finance software unless grounded in verified order, settlement, and cost data. The current app only estimates leakage. | After verified savings, settlement data, and working capital signals are captured with audit trails. |
| Marketplace health | Postponed | Marketplace account health adds policy, listing, claim, review, and platform-specific workflows outside the first wedge. | After the profit recovery control room is repeatable and marketplace data ingestion is reliable. |
| Full customer support inbox | Killed for current product | A support inbox optimizes conversations. Wembro optimizes daily leakage actions and proof. | Only reconsider if the inbox is limited to COD/NDR rescue outcomes and does not become generic support software. |
| AI voice calling | Killed for current product | Voice automation is risky, compliance-heavy, and easy to oversell before pilot proof. | Only after manual rescue scripts, opt-in rules, call audit logs, and measured seller economics exist. |
| ML prediction | Postponed | Current risk scoring must stay explainable and rule-based. Prediction claims need trained data, labels, evaluation, and calibration. | Enough clean labeled seller data, baseline comparison against rules, and documented evaluation results. |
| Real WhatsApp sending | Postponed | The current app uses mock/manual outbox behavior. Real sending requires provider approval, templates, webhooks, opt-outs, and audit logs. | Approved provider integration, consent handling, delivery/reply webhooks, and production audit proof. |
| Real courier API pushes | Postponed | Pushing reattempt, address, or cancellation instructions changes shipment state and needs provider contracts plus traceability. | Courier integration, sandbox/live proof, action audit trail, rollback process, and seller approval rules. |
| Shopify/WooCommerce sync | Postponed | The current wedge must prove CSV-first value before syncing live order data. | Pilot proof, auth/storage hardening, integration implementation, webhook reliability, and reconciliation fallback. |

## Hard No Items

These must not appear as active-product promises, marketing claims, roadmap shortcuts, UI copy, or demo behavior:

- "We send WhatsApp messages" unless a real provider integration and approvals exist.
- "We push courier actions automatically" unless provider integration and audit proof exist.
- "We sync Shopify/WooCommerce automatically" unless explicitly implemented and tested.
- "AI predicts RTO" unless a trained and evaluated model exists and is clearly labeled.
- Guaranteed ROI, guaranteed savings, or verified savings without seller-specific evidence.
- Broad active modules for inventory, returns, settlement, marketplace health, cashflow, store building, or generic chatbot workflows.
- Autonomous execution that skips human approval for risky COD, NDR, address, courier, or cancellation decisions.

## Allowed Current Surface

Wembro may talk about:

- CSV-first order, shipment, and NDR import.
- Rule-based COD/RTO/NDR risk and explainable reasons.
- Address quality checks.
- Daily profit action queue.
- NDR rescue workflow.
- Mock/manual WhatsApp outbox and manual response capture.
- Courier, pincode, SKU, and campaign leakage recommendations when derived from imported data.
- Estimated savings with formulas, confidence, and low-sample warnings.
- Verified savings only when the seller or operator records proof.

Everything else is future architecture until the Revenue Leakage Control Center earns the right to expand.
